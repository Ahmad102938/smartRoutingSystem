# Chapter 2 — System Architecture and Design

This chapter presents the architecture of the Smart Ticket-Routing and Dispatch System. It begins with a high-level overview of how the major components interact, proceeds to the agent-based decomposition that forms the system's intelligent core, then describes the data model and the design rationale behind each schema choice, and concludes with the phased rollout strategy that gates learned-model components on the gradual accumulation of training data.

---

## 2.1 High-Level Architecture Overview

The system is implemented as a single Next.js web application augmented with an in-process AI orchestration layer. From the perspective of an end user — a store register submitting a maintenance ticket, a service provider accepting an assignment, or a moderator verifying completed work — it appears as a conventional database-backed application with sub-two-second response times. Behind that surface, however, every newly created ticket triggers a multi-stage pipeline of specialized agents that together decide which provider receives the work, log every decision for offline learning, and produce an audit-trail rationale asynchronously after the user has already received their response.

### 2.1.1 Architectural Layers

The system is structured into four conceptual tiers, each with a well-defined responsibility and a narrow interface to its neighbours.

The **presentation tier** is a server-side rendered React application built on Next.js's App Router. It surfaces role-specific dashboards for the four user roles in the system — store register, service provider, technician, and moderator — along with form components that capture the inputs required by the AI pipeline. These include the ticket-creation form (which captures the free-text description, the in-store location, and an optional QR-scanned asset identifier), the resolution form filled by the technician, the verification form filled by the moderator, and the per-technician skill editor.

The **API tier** is implemented as Next.js route handlers in the `/app/api` directory. Each route is single-purpose and stateless: authentication and authorization checks are enforced at the boundary, the request payload is validated against a Zod schema, and any non-trivial business logic is delegated to the orchestration tier. This keeps the API thin and the business logic testable in isolation. Notable routes include the ticket-creation endpoint at `/api/tickets`, the resolution endpoint at `/api/tickets/[id]/resolve`, the moderator verification endpoint at `/api/tickets/[id]/verify`, and two cron-triggered worker endpoints that handle asynchronous explanation generation and weekly model retraining.

The **orchestration tier** is the heart of the system. It is implemented as a single class, `AIOrchestrator`, that exposes four public methods corresponding to the four lifecycle events of a ticket: creation, acceptance, rejection, and completion. The orchestrator does not perform analysis or scoring directly; instead, it composes a set of specialized agents, each responsible for one well-defined cognitive task, and threads the necessary context between them. This decomposition is described in detail in Section 2.2.

The **persistence tier** is a PostgreSQL database hosted on Neon's serverless platform, accessed through the Prisma ORM. The `pgvector` extension is enabled on the database, providing native support for high-dimensional similarity search over the 384-dimensional embedding columns added to the `tickets`, `users`, and `assets` tables. All schema migrations are tracked under version control in the `prisma/migrations/` directory and applied via Prisma's deployment workflow.

### 2.1.2 Request Flow for a Newly Created Ticket

The end-to-end flow of a single ticket creation request illustrates the interaction between these tiers. When a store register submits the ticket-creation form, the browser sends a POST request to `/api/tickets` containing the description, the in-store location, and the optional asset identifier. The API tier authenticates the session, verifies the user holds the `ticket:create` permission, validates the payload, and resolves the user's associated store. It then hands control to `AIOrchestrator.processNewTicket`, which sequences the work as follows.

The orchestrator first invokes the classification agent, which sends the free-text description to Google's Gemini 1.5 Flash language model with a strict JSON response schema. The agent returns a structured triple of category, subcategory, and priority along with a confidence score. If the language model is unavailable or the response fails schema validation, the agent transparently falls back to a keyword-based classifier — the system never fails to classify a ticket. The classification result is then passed to the escalation agent, which computes a service-level-agreement deadline based on the priority (four hours for HIGH, twelve hours for MEDIUM, forty-eight hours for LOW). If the ticket carries a QR-scanned asset identifier, the orchestrator performs an upsert into the `assets` table, ensuring that equipment identity is captured from the very first sighting and accumulates over time. The ticket is then persisted with status `OPEN`, and a fire-and-forget background task is dispatched to compute and store the ticket's vector embedding.

The orchestrator next invokes the availability agent, which is responsible for producing the candidate set. This agent fetches all approved service providers, filters them by capacity (using a query-derived live-load count rather than a stale counter column), and computes a coarse composite score for each remaining candidate based on availability, geographic distance, and a fuzzy substring match between the candidate's skill list and the required skills derived from the ticket's classification. The output is a ranked list of candidates that have at least nominal capacity to take the ticket.

This candidate list is then enriched with two semantic features. The orchestrator calls the similarity agent to compute, for each candidate, a cosine similarity between the ticket's text embedding and the highest-scoring associated technician's skill embedding. It also computes an asset-history score: the fraction of past tickets on the same physical asset (or, when available, on other assets of the same make and model) that this candidate has resolved with a positive moderator verdict. Both features default to zero when the underlying data has not yet accumulated, and the system degrades gracefully to its deterministic baseline.

The enriched candidate list is then passed to the routing agent, which performs the final ranking. The routing agent computes a six-feature weighted score for each candidate, applies priority-driven weight adjustments (HIGH-priority tickets bias the formula toward proximity and availability), and selects a candidate. Critically, the selection is not always strictly the top-scored candidate: with a configurable probability (defaulting to ten percent), the routing agent samples uniformly from the top three candidates instead, an exploration mechanism whose purpose is discussed in Section 2.2.4. Before writing the assignment, the agent records the top five candidates with their full feature breakdowns into a `RoutingDecisionLog` row — counterfactual logging that will form the unit of training data for the eventual learned ranker. Only then does it create the `TicketAssignment` row, update the ticket's status to `ASSIGNED`, and return.

The API responds to the user, typically within two seconds. Concurrently, the orchestrator schedules the asynchronous explainer agent via Node's `setImmediate`. The explainer pulls the just-written decision log, the ticket context, and the chosen provider, and asks Gemini to generate a human-readable rationale or flag any concerns. The result is written back to the assignment row, surfaced in administrative dashboards, but never used to override the deterministic decision.

### 2.1.3 Technology Stack and Rationale

The choice of technologies reflects a deliberate balance between developer productivity, operational simplicity, and the specific constraints of an AI-augmented system. Next.js was retained as the application framework because it was already in use and provides a coherent server-side rendering and API model in a single codebase. PostgreSQL was chosen as the database not only for its general reliability but specifically because the `pgvector` extension allows vector search to coexist with relational queries on the same engine, eliminating the operational burden of running a separate vector database such as Pinecone or Weaviate. Prisma was used as the ORM because of its strong type generation and migration tooling, both of which proved essential during a period when the schema was evolving rapidly.

For language-model interactions, Google's Gemini 1.5 Flash was selected over alternatives such as OpenAI's GPT models for two reasons: cost efficiency at the volumes anticipated for production traffic, and the model's native support for structured JSON output via response schemas, which removes an entire category of parsing failures. For embeddings, however, the system explicitly avoids any third-party API and instead runs the open-weight `bge-small-en-v1.5` model locally in-process via the `@xenova/transformers` library. This choice is driven primarily by privacy considerations — ticket descriptions can contain customer names, store identifiers, and other personally identifying information that should not leave the application's infrastructure. A local model also eliminates network latency for what is otherwise a hot-path operation.

LangGraph, a state-machine library for language-model workflows, is retained from the pre-existing codebase but used sparingly. Its only consumer is the escalation agent, which runs as a periodic batch job over open tickets to detect SLA breaches. A deliberate architectural decision was made not to adopt LangGraph for the routing path itself, because doing so would couple ticket-creation latency to the availability of a language model and introduce failure modes that the deterministic routing agent does not have.

## 2.2 Multi-Agent Pipeline Design

The intelligent core of the system is decomposed into a set of single-responsibility agents rather than a single monolithic service. This decomposition is not aesthetic; it reflects a fundamental constraint of building reliable software around language models. Language models are, by their nature, slow, expensive, and occasionally wrong. Wrapping the entire routing decision in a single language-model call would have produced a system that is opaque (one cannot inspect or unit-test the steps), fragile (every routing decision depends on the model's availability), and slow (multi-second latency on every ticket creation). The agent-based design isolates language-model use to the steps where it adds genuine value — natural-language classification and human-readable explanation — and uses fast, deterministic, testable code for everything else.

### 2.2.1 The Orchestrator as Conductor

The `AIOrchestrator` class is the only component that knows the order in which agents must run. The agents themselves have no awareness of one another; they receive plain data inputs and return plain data outputs. This pattern keeps each agent simple and independently testable, while concentrating the temporal and transactional concerns of the pipeline into a single file. The orchestrator owns the four ticket-lifecycle methods: `processNewTicket`, `handleTicketAcceptance`, `handleTicketRejection`, and `handleTicketCompletion`. Of these, `processNewTicket` is the most elaborate, sequencing the seven-step pipeline described in Section 2.1.2.

A consequence of this design is that the orchestrator is the single source of truth for agent ordering. If a future requirement demands, for instance, that the explainer agent's output be considered before the routing agent commits its choice (a hypothetical workflow in which AI disagreement would auto-trigger re-ranking), only the orchestrator changes; the agents themselves remain untouched. This separation has already proven valuable during development, where the order of operations was revised three times without requiring changes to the agents themselves.

### 2.2.2 The Classification Agent

The classification agent is the only language-model consumer on the request path. Its responsibility is to translate a free-text problem description into a structured triple suitable for downstream consumption: a category (such as `Facilities` or `IT`), a subcategory (such as `Cold Storage` or `POS Systems`), and a priority (`HIGH`, `MEDIUM`, or `LOW`). It also returns a confidence value and a brief reasoning string, both of which are stored alongside the ticket for future analysis.

The agent is built around Gemini 1.5 Flash with `responseMimeType: 'application/json'` and a strict response schema that the model must conform to. The output is further validated against a Zod schema in the agent itself; mismatches cause a fallback to a keyword-based classifier that uses simple substring matching to assign reasonable defaults (for example, the presence of "freezer" or "cooling" in the description maps to `Facilities/Cold Storage/HIGH`). The fallback exists because the classification result feeds the SLA computation and the skill mapping that drives candidate selection — a missing classification would block the entire pipeline, and the cost of an imperfect classification is significantly lower than the cost of a failed ticket creation.

The priority output deserves special attention because of its downstream effects. The escalation agent reads it directly to compute the service-level-agreement deadline. The routing agent reads it to apply weight adjustments: for HIGH-priority tickets, the weights for proximity and availability each increase by ten percentage points, drawn from corresponding decreases in the weights for skill match, semantic similarity, and asset history. The implicit thesis is that for an urgent ticket, the marginal cost of a less-than-perfect skill match is outweighed by the benefit of getting somebody on site quickly.

### 2.2.3 The Availability Agent

The availability agent operates as a coarse filter and ranker. Its input is the set of skills required for the ticket (derived from a static category-to-skills map maintained in the orchestrator) and the geographic coordinates of the store. Its output is a ranked list of candidate service providers, each annotated with a distance, a derived live-load count, an availability score, a skill-match score, and a composite overall score.

The most consequential design decision in this agent is the abandonment of the previously-stored `current_load` integer column on the `ServiceProvider` table. In the legacy system, this column was incremented and decremented from three different code paths — when a routing decision was committed, when an assignment was rejected, and when a ticket was completed — with no transactional guarantees binding the counter update to the assignment write. Any failure between the two operations would silently corrupt the counter, and the corruption would persist indefinitely. The availability agent now derives the live load by issuing a single grouped count query against the `TicketAssignment` table for assignments whose status is `PROPOSED` or `ACCEPTED`. This query is correct by construction: it cannot drift, it requires no maintenance, and it transparently extends to per-technician load tracking when individual users (rather than companies) are the assignment target.

The skill match in this agent is a fuzzy bidirectional substring match: a required skill matches a provider skill if either string is contained in the other, case-insensitively. This is intentionally permissive — providers without any matching skills are not eliminated from the pool, only scored zero on this axis. The decision to pass them downstream rather than filter them out is conservative: in real operational data, exact skill names rarely match the formal taxonomy used in the category map, and an over-aggressive filter would frequently leave the system with no candidates at all. The downstream routing agent applies the strict ranking; the availability agent's job is only to ensure the candidate has the capacity and physical presence to take work.

### 2.2.4 The Routing Agent

The routing agent performs the final ranking and assignment. It operates on the enriched candidate list produced by the availability agent and the similarity agent (described next), and it produces three durable artifacts: a `RoutingDecisionLog` row capturing the full set of considered candidates, a `TicketAssignment` row assigning the ticket to the chosen candidate, and a status update on the `Ticket` row itself.

The agent's central computation is a six-feature weighted score for each candidate. The features are: skill match (weighted at thirty percent of the base score), proximity (twenty percent), availability (fifteen percent), semantic similarity to the candidate's accumulated skill profile (fifteen percent), asset-history good-outcome ratio (ten percent), and historical performance ratio (ten percent). Priority adjustments shift up to twenty percentage points across these weights when the ticket is HIGH-priority. The total weight always sums to one, so the resulting score lies in the unit interval and is directly comparable across candidates and across time.

A critical and counter-intuitive feature of this agent is its exploration mechanism. With a probability controlled by the `ROUTING_EXPLORATION_RATE` environment variable (defaulting to ten percent), the agent does not pick the top-scored candidate; instead, it samples uniformly from the top three. The chosen assignment is flagged with `was_exploration=true` so that downstream training and analysis can account for it. The motivation for this design is the well-known problem of selection-bias poisoning in learned ranking systems: a model that only ever observes outcomes for candidates the policy already preferred will, when retrained, simply memorize the policy that produced its training data. Exploration introduces controlled variance into the policy's decisions, ensuring that the eventual learned ranker has access to outcomes from candidates it might otherwise never have seen. The cost is small — occasionally choosing a slightly worse candidate — and the benefit is the ability to learn anything new at all.

The agent also writes a counterfactual decision log before committing the assignment. The log captures the top five candidates, their full feature breakdowns, the chosen candidate, and the exploration flag. This log is the unit of training data for Phase 4 of the rollout: a future XGBoost LambdaRank model will train pairwise over the candidates within each log row, leveraging the fact that the policy's preferences over alternatives are recorded even though only the chosen candidate's outcome is ground-truth observed.

### 2.2.5 The Similarity Agent

The similarity agent is the system's interface to vector search. It is invoked by the orchestrator immediately before routing to enrich the candidate list with two semantic features. Internally it has three responsibilities. First, given a ticket-text input, it embeds the text using the local `bge-small-en-v1.5` model and runs a cosine-distance query against the `users.skill_embedding` column to rank technicians by semantic fit; the maximum similarity over the technicians belonging to each candidate company becomes that candidate's `semantic_similarity` feature. Second, given an asset identifier, it queries the historical record of past tickets on the same asset (or the same make and model) and computes, for each candidate, the fraction of those tickets that ended with a positive moderator verdict. Third, when a moderator submits a positive verdict on a ticket, it refreshes the resolving technician's skill embedding by re-embedding the concatenated `root_cause` and `technician_notes` text from the technician's last twenty positively-verified outcomes.

The decision to run embeddings locally rather than via a third-party API is the most consequential architectural choice in the similarity agent. The `bge-small-en-v1.5` model is roughly thirty megabytes on disk, runs in approximately thirty milliseconds per inference once warm, and produces 384-dimensional vectors that are competitive with much larger models on retrieval-quality benchmarks. By keeping the model in-process, the system never sends ticket text to an external service, which is essential given that ticket descriptions frequently contain personally identifying information.

The agent's behavior under cold-start conditions deserves explicit mention because it is central to the system's graceful-degradation property. Until the first several dozen ticket outcomes have been positively verified, no technician has a non-null skill embedding, and so the semantic similarity feature returns zero for every candidate. Similarly, until ratings have accumulated for tickets on a given asset, the asset-history score is zero. The routing agent treats both features as numeric inputs and continues to function correctly; the only effect is that the deterministic features (skill match, proximity, availability, performance) carry the full weight of the decision. As outcomes accumulate, the learned signals begin to contribute, and the system's behaviour shifts smoothly from heuristic-driven to learning-augmented without any manual cutover.

### 2.2.6 The Explainer Agent

The explainer agent runs entirely off the request path. It is triggered both by an inline `setImmediate` call after every successful routing decision and by a scheduled cron sweep over any assignments left in the `PENDING` state. Its purpose is to produce a human-readable rationale for the routing decision and to surface concerns when the heuristic appears to have made a poor choice.

The agent uses the same Gemini 1.5 Flash model as the classification agent, with a structured response schema that returns four fields: an `appropriate` boolean indicating whether the pick looks reasonable, a `confidence` value, a multi-sentence `rationale`, and an optional list of specific `concerns`. The output is written back to the assignment row in the `explanation`, `explanation_status`, and `ai_disagreement` columns. The `ai_disagreement` flag is set only when the model returns `appropriate=false` with confidence above a threshold of 0.6; this is surfaced in administrative dashboards as an audit signal but does not trigger automatic re-routing. The explicit decision to leave action in human hands reflects the principle that an unreliable signal — and a language model's confidence value is by no means a reliable probability — should inform decisions, not make them.

The async-only design of this agent is in deliberate contrast to a tempting alternative in which the explainer runs synchronously and its output influences the routing decision itself. That alternative was rejected for two reasons. First, putting a language-model call on the request path would push ticket-creation latency from under two seconds to over five, with high tail variance. Second, an outage of the language-model provider would prevent any ticket from being assigned. The async pattern preserves both fast user response times and graceful degradation: when Gemini is unavailable, assignments still happen, and the explanations simply queue up to be processed when service is restored.

### 2.2.7 The Escalation Agent

The escalation agent predates this work but is a relevant part of the pipeline. It is implemented as a LangGraph state machine and runs as a periodic batch over all open tickets. For each ticket, it checks three SLA thresholds — assignment timeout, acceptance timeout, and resolution timeout — and writes an `Escalation` row when a threshold is breached. The escalation agent is the architectural precedent that informed the asynchronous design of the explainer: both run off the request path, both operate over batches of pending rows, and both modify state without blocking user-facing operations.

## 2.3 Data Model and Schema Design

The data model evolved substantially during this work. The original schema, designed before the AI dispatch system existed, modeled the basic entities of a maintenance-ticket workflow: `User`, `Store`, `ServiceProvider`, `Ticket`, and `TicketAssignment`. While these entities remained foundational, they did not carry sufficient information to support intelligent routing or continuous learning. Five new entities were introduced, three existing entities were extended with new columns, and several invariants of the data model were rewritten to support polymorphic assignment targets and learned features.

### 2.3.1 Pre-Existing Core Entities

The pre-existing entities continue to fulfill the same conceptual roles but were extended where necessary. The `User` table represents authentication identity and is partitioned by role into store registers, service-provider operators, technicians, administrators, and moderators. The `TECHNICIAN` role was added to the `UserRole` enumeration to support direct assignment to individual technicians, complementing the existing `SERVICE_PROVIDER` role which represents users acting on behalf of a service-provider company.

The `Store` table represents a physical retail location and includes a JSON-encoded set of geographic coordinates that the routing pipeline uses for distance calculations. The `ServiceProvider` table represents a company-level vendor with a string array of skills, a daily capacity, a primary geographic location, and an approval status. The `Ticket` table is the central entity of the workflow, carrying the description, classification, location, status, and SLA deadline. The `TicketAssignment` table represents the relationship between a ticket and a candidate provider; it can transition through the states `PROPOSED`, `ACCEPTED`, `REJECTED`, and `EXPIRED`, and it is now the authoritative source for the question of who currently owns a ticket.

### 2.3.2 New Entities

Five new entities were introduced to support the routing system and the continuous-learning loop.

The **`Asset`** entity represents a piece of physical equipment identified by the QR code the store register scans during ticket creation. In the legacy system, the QR code was captured as a free-form string on the ticket and never used for any analytical purpose. In the new system, the orchestrator performs an upsert into the `Asset` table on every ticket creation, ensuring that the asset's identity is captured the first time it appears and accumulates history with each subsequent ticket. The asset's optional `make`, `model`, `category`, and `description` fields can be enriched manually through the asset-management API, and an embedding column allows the asset to participate in semantic similarity queries. The relationship between `Ticket` and `Asset` is a many-to-one foreign key; multiple tickets can reference the same asset, which is essential for computing the asset-history feature in the routing agent.

The **`TechnicianSkill`** entity captures per-technician skills with a proficiency level (`NOVICE`, `COMPETENT`, or `EXPERT`) and an optional years-of-experience value. This was introduced to address a fundamental shortcoming of the legacy schema: skills were stored as a string array on the `ServiceProvider` table at the company level, with no way to distinguish between an electrician with twenty years of experience and a junior employee at the same company. With per-user skills, the routing system can build technician-specific profiles, compute meaningful semantic embeddings of those profiles from outcome data, and eventually route to specific individuals rather than to companies. A unique constraint on `(user_id, skill)` prevents duplicate skill rows for the same user.

The **`TicketOutcome`** entity captures the resolution data submitted by the technician when a ticket is completed. It includes the resolution time in minutes, a first-time-fix boolean, the identified root cause, an optional list of parts used (stored as JSON to accommodate variable structure), and free-text technician notes. Two reassignment fields — `was_reassigned` and `reassignment_count` — are populated automatically from the ticket's assignment history. The `TicketOutcome` is the technician-facing analogue of the resolution form and is required before a ticket can transition into the verification phase.

The **`TicketRating`** entity is the moderator's verdict on the resolution. It is a deliberately simple structure: a binary `verdict` field with values `GOOD` or `BAD`, an array of optional tags drawn from a small predefined vocabulary, and an optional comment. The simplicity is intentional — the entity exists primarily to produce a high-signal binary label suitable for training a ranking model, and richer rating structures (such as numeric scores) introduce subjective variance that a binary verdict avoids. A `GOOD` verdict closes the ticket; a `BAD` verdict reopens it for re-attempt or reassignment. The `TicketRating` is the entity that produces the ground-truth label feeding the entire learning loop, and its accuracy is therefore one of the most operationally important properties of the system.

The **`RoutingDecisionLog`** entity is the counterfactual training-data substrate. For every routing decision, the routing agent writes a row containing the top five candidates with their full score breakdowns, the picked candidate's identifier, and a flag indicating whether the choice was an exploration sample. The log retains this information regardless of the eventual outcome, allowing offline trainers to compute per-candidate features and to use the log as a unit of training signal in pairwise ranking algorithms.

### 2.3.3 Schema Extensions to Existing Entities

Several existing tables were extended with new columns to support the routing system. The `Ticket` table received an `asset_id` foreign key referencing the new `Asset` table, and an `embedding` column of type `vector(384)` storing the bge-small embedding of the ticket's text. The `User` table received a `skill_embedding` column of the same type, populated from outcome data for technicians who have accumulated positively-verified resolutions. The `Asset` table includes its own `embedding` column for asset-level similarity queries.

The `TicketAssignment` table received the most extensive set of additions. A nullable `assigned_user_id` foreign key was added to support per-technician assignment targets, complementing the existing company-level `service_provider_id`; both can be set simultaneously when a named technician at a specific company is assigned to the work. A `was_exploration` boolean records whether the assignment was the result of the routing agent's exploration mechanism. Four columns related to the explainer agent — `explanation`, `explanation_status`, `ai_disagreement`, and `explained_at` — capture the asynchronously generated rationale and metadata. Indexes were added on `(assigned_user_id, status)` and `(service_provider_id, status)` to support efficient live-load queries, and on `explanation_status` to support the cron sweep that processes pending explanations.

### 2.3.4 Polymorphic Assignment Design

The most architecturally significant data-model change is the polymorphic assignment target on `TicketAssignment`. The new design supports three cases simultaneously: assignment to a service-provider company (the legacy case, where `service_provider_id` is set and `assigned_user_id` is null), assignment to a specific technician within a company (where both fields are set), and assignment to an independent technician (where only `assigned_user_id` is set and `service_provider_id` may be null in a future extension). This design was chosen over three alternatives: an exclusive-or constraint between the two foreign keys, a discriminator column with single-table-inheritance semantics, and two separate join tables. The dual-foreign-key approach was selected because the data is genuinely both — the company-and-named-technician case is the most common in operational practice, and forcing a choice between the two would lose information.

### 2.3.5 Live Load as a Derived Quantity

A subtle but operationally significant change is that the `current_load` integer column on `ServiceProvider` is no longer mutated by the application. Instead, the availability agent derives the current load on each invocation by issuing a grouped count query over `TicketAssignment` rows whose status is `PROPOSED` or `ACCEPTED`. This change addresses a class of bugs that had silently corrupted the counter in the legacy system: any failure between the assignment write and the counter increment, or any code path that wrote to one without the other, would leave the counter inconsistent indefinitely. The derived-query approach makes correctness a property of the schema rather than a property of every code path that touches it.

### 2.3.6 Vector Columns and Indexes

The `pgvector` extension is enabled on the production database via a dedicated migration. Three columns of type `vector(384)` were added — one each on `tickets`, `users`, and `assets` — and each is backed by an HNSW (Hierarchical Navigable Small World) index using the `vector_cosine_ops` operator family. HNSW provides approximate nearest-neighbour search with logarithmic complexity and is well-suited to the workload anticipated for this system, where the number of indexed vectors will remain in the low hundreds of thousands even at significant scale. The choice of 384 dimensions matches the output of `bge-small-en-v1.5`; should a future migration to a different model be desired, the column type can be altered and the index rebuilt without changing application code.

### 2.3.7 Source-of-Truth Migration

The data model carries one piece of intentional duplication. The `Ticket.assigned_service_provider_id` column, which previously held the canonical answer to the question of which provider was assigned to a ticket, is retained as a denormalized read cache. The authoritative source has shifted to the most recent active `TicketAssignment` row, but multiple read sites in the legacy codebase still query the denormalized field. A complete sweep of those sites would have constituted a high-blast-radius refactor, and the highest-value sites — the role-based access control function `getTicketContext` and the SERVICE_PROVIDER ticket-list filter — were migrated to read through `TicketAssignment` first, with the denormalized field retained as a fallback for legacy data. The remaining read sites continue to function correctly because the routing agent still writes the denormalized field on every assignment; the migration is therefore safe to complete incrementally.

## 2.4 Phased Rollout Strategy

The system is engineered to be deployed in five sequential phases, each gating on the data or operational maturity that the next phase requires. This phasing is not a project-management convenience; it reflects a hard constraint on learning systems, namely that no machine-learned model can outperform the quality and quantity of its training data, and that data must be collected through real production use over time.

### 2.4.1 The Cold-Start Problem

Any learning system must navigate the cold-start problem: until a sufficient body of labelled data has accumulated, a learned model has nothing meaningful to learn from, and forcing one into production prematurely produces a system that is both unreliable and expensive. A common but serious anti-pattern is to deploy a learned ranker that has been trained on synthetic data, on data borrowed from another product, or on the policy's own historical decisions without exploration; in each case the model memorizes biases that compound rather than correcting them. The phased rollout adopted here treats learning components as the final destination and ensures that every preceding phase contributes to the training data that the learning components will eventually require. The system delivers value at every phase, with or without the learned components; no phase blocks the previous phase from operating in production.

### 2.4.2 Phase Zero — Cheap Wins

Phase zero comprises three independently shippable changes that establish the data foundations for everything that follows. The first is the deletion of dead code in the routing agent — a Gemini SDK initialization block that was instantiated in the constructor but never called by any method. Misleading dead code in a file scheduled for redesign is a debugging tax on every future contributor and was removed at the earliest opportunity. The second is the introduction of the `Asset` entity and the upsert path that captures equipment identity from the first QR scan. This change is small in scope but high in long-term value: every day that passes without it is a day of asset history irretrievably lost. The third is the introduction of the `RoutingDecisionLog` table and the corresponding write in the routing agent. Counterfactual logging from day one is essential because the value of the log compounds with time: every routing decision recorded today is a training row available to the eventual learned ranker.

### 2.4.3 Phase One — Data Foundation

Phase one is the most extensive of the five phases and constitutes the bulk of the engineering effort. It introduces the schema models that capture outcomes and ratings (`TicketOutcome`, `TicketRating`, `TechnicianSkill`), the API endpoints that allow operators to populate those models (`/api/tickets/[id]/resolve`, `/api/tickets/[id]/verify`, `/api/technicians/[id]/skills`, `/api/assets`), and the front-end forms that wrap those endpoints in usable interfaces. It also introduces the live-load refactor that replaces the manually-mutated counter with a derived query, and the exploration mechanism in the routing agent. The phase explicitly does not introduce any learned components; its purpose is to prepare the substrate from which learning will eventually become possible.

The phase has a natural gating point: the embeddings introduced in Phase 2 require text data of a kind that only Phase 1's `TicketOutcome.technician_notes` and `root_cause` fields can provide. Premature embedding generation on synthetic or borrowed data would produce semantic features that encode the biases of the source, not the realities of the system's actual operational domain. Phase 1 must therefore run for several weeks before Phase 2 can produce meaningful results.

### 2.4.4 Phase Two — Embeddings and Semantic Similarity

Phase two introduces the `pgvector` extension, the three vector columns, the local embedding pipeline, and the similarity agent. The agent is fully operational from the moment it ships, but its outputs default to zero until the supporting data has accumulated. The routing agent's score formula is updated to incorporate the two semantic features as additional terms in the weighted sum, with weights chosen so that the deterministic features continue to dominate during the cold-start period.

The phase is designed so that no operational change occurs at the moment of deployment. In the absence of skill embeddings, the routing decisions are arithmetically identical to those that would have been produced by the Phase 1 system. As technicians accumulate positively-verified resolutions and their skill embeddings populate, the semantic features begin to contribute, and the routing decisions shift smoothly. This gradual transition is by design: it allows operators to observe the effect of the new features incrementally rather than as a step change.

### 2.4.5 Phase Three — Asynchronous Language-Model Explainer

Phase three introduces the explainer agent, the cron worker that processes its pending queue, and the schema columns that store its output. This phase has no data-accumulation dependency and can ship at any time after Phase 1; in practice it ships immediately after Phase 2. The explanations begin appearing on assignments within seconds of their creation, providing audit trails for administrators and a sanity-check signal (`ai_disagreement`) for moderator review.

Phase 3 is the first phase that depends on the availability of Google's Gemini API for production functionality. Critically, the system continues to function correctly during Gemini outages: assignments are still written, explanations simply queue up in the `PENDING` state, and the cron sweep processes them when service is restored. The system's correctness does not depend on the explainer's correctness, only on its eventual availability.

### 2.4.6 Phase Four — Learned Ranker

Phase four introduces the learned ranking model. The phase is scaffolded but inert in the codebase as shipped: the feature builder, the Node-side ranker client, the training-data exporter, and the Python FastAPI sidecar with its XGBoost training script all exist, but the routing agent does not consult the sidecar unless the `ENABLE_LEARNED_RANKER` environment variable is set to `1` and the `RANKER_SIDECAR_URL` is configured. The training script itself refuses to run with fewer than two hundred labelled rows.

The realistic gate to Phase 4 deployment is the accumulation of approximately one thousand labelled outcomes — that is, one thousand tickets that have been completed, verified by a moderator, and assigned a `GOOD` or `BAD` verdict. At a representative throughput of fifty tickets per week with a sixty-percent verification rate, this requires approximately thirty weeks of sustained production operation. This timeline is not a pessimistic estimate; it is a hard constraint imposed by the need for exploration data, label quality, and statistical confidence in cross-validation. Phase 4 cannot be shortened by deploying the model earlier with less data.

### 2.4.7 Phase Five — Continuous Improvement

Phase five comprises the operational loop that keeps the learned ranker calibrated over time. It introduces drift dashboards that surface acceptance rate, first-time-fix rate, SLA compliance, AI disagreement rate, and per-category accuracy — both for operational monitoring and for early detection of model decay. It introduces a weekly retrain cron that exports the latest training data, optionally pushes it to a configured webhook, and triggers a hot reload on the FastAPI sidecar. It introduces blue-green model deployment, in which a newly trained model must demonstrate improvement on a held-out evaluation set before replacing the current production model. And it introduces A/B testing infrastructure behind a feature flag, allowing a fraction of stores to receive routing decisions from a candidate model while the remainder continue with the production model.

In the current shipped state, the drift dashboards are operational and the retrain cron is implemented as a stub: it exports the data and reports on its readiness for training, but does not yet trigger the training script. Full Phase 5 functionality activates with Phase 4.

### 2.4.8 The Phasing Rationale in Summary

The phased rollout reflects three principles. First, every phase must deliver value independently — the system is useful at the end of Phase 0, more useful at the end of Phase 1, and so on, without any phase creating a dependency that prevents production deployment until later phases ship. Second, learned components must gate on the data they require, and that data must be collected through real production use rather than synthesized; this is why Phases 4 and 5 are explicitly described as future-deployed in the report's current state. Third, no phase introduces irreversible coupling to a future component — the learned ranker can be disabled and the system reverts smoothly to the deterministic policy, the explainer can be disabled and assignments continue without rationales, and even the embedding system can be disabled and the routing agent falls back to its non-semantic features. Each component is additive, never load-bearing in a way that creates a single point of failure.

This is the core design discipline of the system: every layer is correct on its own terms, and every learned layer makes the system smarter without making it more fragile.
