## 8.1 Summary of Work Done

### 8.1.1 The Problem the System Was Built to Solve

The legacy ticket-routing system at the start of the internship was a hand-tuned weighted scorer that combined fuzzy substring matching of skill names, geographic distance via Haversine, capacity-based load tracking through a manually-maintained counter column, and a binary completed-versus-not performance ratio. The system never learned from the outcomes of its decisions; the same matching mistakes recurred regardless of how often they had been made before. The QR codes captured during ticket creation were stored as orphaned strings without any associated equipment-history table. Skills were modeled at the company level, with no representation of individual technician expertise. There was no rating mechanism, no feedback loop, no exploration of routing alternatives, and no infrastructure for evolving toward a learned ranking model. The Gemini SDK initialization in the routing agent was dead code, never invoked by any method but contributing to confusion about what the system actually did.

The internship was assigned the task of redesigning this routing system into a closed-loop, multi-agent dispatch engine that would make intelligent decisions with the available data, log every decision in counterfactual detail for offline analysis, learn from outcome verifications over time, and degrade gracefully under the absence of any individual learned signal. The work proceeded through five engineering phases, each producing artifacts that were either immediately operational or structurally complete in preparation for activation when sufficient data had accumulated.

### 8.1.2 The Architectural Contribution

The most consequential output of the internship is the system's overall architecture, described in Chapter 2. The legacy system was a single thread of business logic in which the routing decision and its persistence were interleaved with capacity tracking and other concerns. The redesigned system decomposes the routing pipeline into a central orchestrator and a collection of single-responsibility agents, with each agent receiving plain data inputs and returning plain data outputs and the orchestrator owning the temporal sequencing and transactional shape of state changes.

This decomposition is the foundation that everything else rests on. Without it, the addition of a similarity agent, an asynchronous explainer, and a learned-ranker client would have required surgical modifications to a tangled main flow. With it, each new component is a clean addition that the orchestrator composes alongside the existing components. During the internship the orchestrator's pipeline was revised three times — once to add the asset upsert before ticket creation, once to add the similarity-feature enrichment between availability and routing, and once to add the asynchronous explainer trigger after routing — and each revision was a localized change that did not affect any other component.

### 8.1.3 The Multi-Agent Pipeline

The agents themselves are described in Chapter 3 and form the second principal contribution. The classification agent, which existed in the legacy system as a partial implementation, was extended with structured-JSON output via Gemini's response schema and a complete keyword-based fallback for when the language model is unavailable. The availability agent was substantially redesigned: its load-tracking mechanism was replaced with a query-derived count over the assignment table, eliminating a class of silent-drift bugs that the manual counter had silently accumulated. The routing agent was rewritten end-to-end: the dead Gemini code was removed, the score formula was extended from four features to six, the priority-driven weight adjustment was added, and the ε-greedy exploration mechanism was introduced. The similarity agent was newly built, providing semantic-similarity ranking, asset-history scoring, and skill-embedding refresh against pgvector columns. The explainer agent was newly built, running asynchronously off the request path and producing audit-trail rationales via Gemini.

Each of these agents is now a distinct module in the codebase with a single responsibility, a tested interface, and a clear failure-mode behavior. Their composition by the orchestrator forms a pipeline that is both more capable than the legacy system and substantially more inspectable.

### 8.1.4 The Data Model Contribution

The data model was extended with five new entities — `Asset`, `TechnicianSkill`, `TicketOutcome`, `TicketRating`, and `RoutingDecisionLog` — each addressing a specific gap in the legacy schema. The `Asset` model captures equipment identity from the QR scan, allowing per-asset history to be accumulated and queried. The `TechnicianSkill` model represents individual technician expertise with proficiency levels, enabling per-tech routing in addition to per-company routing. The `TicketOutcome` model captures the structured resolution data submitted by technicians. The `TicketRating` model captures the moderator's binary verdict that serves as the ground-truth label for the continuous-learning loop. The `RoutingDecisionLog` model captures the counterfactual record of every routing decision, including the unchosen alternatives and their feature breakdowns.

Beyond the new entities, several existing entities were extended. The `User` enum gained a `TECHNICIAN` role to support direct technician assignment. The `TicketAssignment` table received an `assigned_user_id` foreign key for polymorphic routing targets, a `was_exploration` flag for downstream training analysis, and four columns supporting the asynchronous explainer's lifecycle. The `Ticket`, `User`, and `Asset` tables each received a `vector(384)` embedding column, indexed via pgvector's HNSW algorithm for fast approximate nearest-neighbor queries.

Three migrations were applied to the production database during the internship: the smart-dispatch foundation migration that introduced the new entities and most of the column extensions, the pgvector migration that enabled the extension and added the vector columns and indexes, and the explainer migration that added the asynchronous-rationale columns. All three migrations were applied successfully and verified end-to-end.

### 8.1.5 The Continuous-Learning Infrastructure

The continuous-learning loop, described in Chapter 5, is the third principal contribution. It comprises four interlocking components.

The moderator-verification flow is the input to the loop. A new API endpoint at `/api/tickets/[id]/verify` accepts a binary verdict with optional tags, persists a `TicketRating` row, and transitions the ticket either to `CLOSED` (on `GOOD`) or back to `IN_PROGRESS` (on `BAD`). The reopening behavior on `BAD` verdicts aligns operational and analytical incentives by ensuring that a moderator's negative verdict has direct consequences rather than being merely a label. A frontend dialog component supports moderators in submitting verifications efficiently.

The skill-embedding refresh is the propagation step of the loop. On every `GOOD` verdict, the verify endpoint dispatches a fire-and-forget call to the similarity agent to recompute the resolving technician's skill embedding from their last twenty positively-verified resolutions. The recomputation runs entirely in-process via the local bge-small embedding model, with no transmission of ticket text to any external service.

The training pipeline is the offline component of the loop. A feature-builder module provides a single source of truth for the per-candidate feature vector, used both at request time by the routing agent and at training time by the offline exporter. An exporter module joins the routing decision log against outcomes and ratings to produce JSONL training data. A Python FastAPI sidecar holds the trained XGBoost LambdaRank model in memory and serves per-candidate scores via a `/rank` endpoint. A Node-side ranker client consumes the sidecar with a one-hundred-millisecond timeout and falls back to the deterministic score when the sidecar is unavailable. All four of these components are structurally complete; the sidecar and ranker client are inert in the current state, awaiting the accumulation of training data sufficient to train a meaningful first model.

The drift-monitoring infrastructure is the operational visibility layer of the loop. A metrics module exposes three computations — overall routing metrics, per-category accuracy, and per-provider performance — via a single administrative API endpoint. The metrics support three complementary modes of drift detection: trend analysis over time, threshold alerting on absolute values, and cohort comparison across categories or providers. A weekly retrain cron endpoint serves as the scaffold for automated model lifecycle management; in the current state it exports training data and reports readiness rather than triggering training automatically.

### 8.1.6 The Frontend Contribution

Three frontend components were built to support the new flows. The resolution form, used by technicians to submit resolution data, captures the resolution time, the first-time-fix flag, the root cause, the technician notes, and an optional list of parts used with quantities and costs. The verification form, used by moderators to verify completed resolutions, supports the binary verdict and a tag selector with verdict-specific tag vocabularies. The skill editor, used by technicians to maintain their skill profiles or by moderators to edit profiles on others' behalf, supports the per-skill proficiency level and years-of-experience values along with a quick-add panel for common skills.

Each component follows the existing application's UI conventions, uses the shadcn/ui primitives, and integrates with the existing toast-notification and authentication systems. The components are simple but functional and provide the user-facing surface required for the continuous-learning loop to operate.

### 8.1.7 The Documentation Contribution

The internship produced substantial technical documentation alongside the code. The architectural reference document at `docs/smart-routing-architecture.md` provides a complete top-to-bottom description of the system as built. The seven preceding chapters of this report — covering the system architecture, the agents, the scoring engine, the continuous-learning loop, the design decisions, and the testing — document not only what was built but the rationale for each significant design choice and the alternatives that were considered and rejected.

The documentation is intended to serve two audiences. The first is future maintainers of the system, who will need to understand why each architectural decision was made before they can responsibly modify it. The second is examiners and reviewers of the internship work, who will use the documentation to evaluate the depth of engineering judgment that the work reflects. The documentation is consistently formal in tone, structured to be navigable both linearly and by section, and explicit about the boundaries of what was and was not done.

### 8.1.9 The Engineering Principles That Ran Through the Work

Three principles ran consistently through the internship work and are worth naming explicitly as the report's intellectual conclusion.

The first is correctness by construction over correctness by coordination. Wherever a choice existed between maintaining application-level synchronization between two pieces of state (such as the legacy counter-based load tracking) or deriving one piece of state from the other on demand (such as the redesigned query-based load tracking), the system preferred the derivation. The cost of this preference was occasionally a small additional database query; the benefit was the elimination of a class of bugs that no amount of careful application coding can fully prevent.

The second is operational defensibility over architectural sophistication. Wherever a choice existed between an apparently more sophisticated design that depended on the availability or speed of an external service (such as LLM-driven routing on the request path) and a less sophisticated design that did not (such as deterministic routing with deterministic fallbacks), the system preferred the latter. The cost of this preference was forgoing certain capabilities the more sophisticated design would have offered; the benefit was a system that runs correctly under partial failure and that can be deployed without acquiring operational dependencies on external providers' uptime.

The third is graceful degradation over capability gating. Wherever a choice existed between requiring a learned component to have sufficient data before any feature depending on it could be enabled, and allowing the feature to operate with sensible defaults until the data accumulated, the system preferred the latter. The cost of this preference was that learned features contribute nothing to routing decisions during their cold-start period; the benefit was a system that is operationally correct from its first ticket onward and that improves continuously rather than at threshold-triggered transitions.

Each of these principles is individually small but together they form an engineering character. The system was built, and the work documented in this report was performed, with these principles consistently in mind.

## 8.2 Future Scope — Learned Ranker Activation

### 8.2.1 The Current State

At the conclusion of the internship, the system's learned-ranker pipeline is structurally complete but operationally inert. The Python FastAPI sidecar exists and serves a `/health` endpoint that reports `model_loaded: false`; the `/rank` endpoint returns a five-hundred-three error indicating the model is not ready. The Node-side ranker client exists and is gated behind the `ENABLE_LEARNED_RANKER` environment variable, which is unset in production. The exporter exists and is runnable, but its output contains too few labeled rows to support training. The training script exists and refuses to run with fewer than two hundred labeled rows.

This state is the deliberate result of the design choices documented in earlier chapters. The system does not deploy a model trained on synthetic or borrowed data, because such a model would memorize biases that compound rather than correct. It does not deploy a model trained on too few real outcomes, because the resulting model would be statistically meaningless and would degrade routing quality. The current state is the state appropriate to the moment in the system's lifecycle where the data foundation has been built but the data has not yet accumulated.

The future scope discussed in this section is the pathway from this state to one in which the learned ranker is the production scoring mechanism, replacing the deterministic six-feature score documented in Chapter 4. The pathway has six identifiable stages, each with specific data requirements, validation criteria, and decision points. Figure 8.2 illustrates the stages.

### 8.2.2 Stage One: Data Accumulation

The first stage is the longest and the least active. It consists simply of running the system as it currently stands and allowing the moderator-verification flow to populate the `TicketRating` table over time. The realistic accumulation rate, as discussed in Chapter 5, is approximately thirty-three labeled outcomes per week given a typical ticket volume of fifty per week and a moderator-verification completion rate of sixty percent. At this rate, the threshold of one thousand labeled outcomes is reached in approximately thirty weeks.

Several activities are appropriate during this stage even though the principal goal is passive accumulation. The drift dashboard should be consulted weekly to confirm that the moderator-verification completion rate is meeting expectations; a sudden drop in the rate indicates either operational fatigue (which can be addressed with workflow improvements) or a UI issue (which can be fixed). The exploration rate should be observed to confirm that the ε-greedy mechanism is producing approximately ten percent exploration assignments; an anomalously low rate would indicate a configuration issue that should be corrected before the data is used for training.

Periodically — perhaps monthly — the exporter should be run and the resulting JSONL inspected for sanity. The principal sanity checks are that the labeled fraction of rows is rising, that the `was_exploration` flag is approximately balanced across explored and exploited decisions, and that the per-candidate feature breakdowns contain the values expected from the routing-agent's score formula. Any anomaly should be investigated before more data accumulates with the same defect.

### 8.2.3 Stage Two: First Training and Evaluation

When the labeled-row threshold has been reached, the first training run is performed. The exporter is invoked to produce the complete JSONL file, the file is transferred to the environment hosting the training script (which may be a local development machine, a notebook environment, or a cloud-hosted training instance), and the training script is run. The script trains an XGBoost LambdaRank model using the pairwise ranking objective described in Chapter 5, applies appropriate regularization, and produces a model file along with a version identifier.

The principal evaluation is offline. A held-out fraction of the data, perhaps twenty percent, is set aside before training and used to compute the model's predicted-vs-actual outcome correlation. The simplest meaningful metric is the ranker's normalized discounted cumulative gain at position one, which measures how often the model's top-ranked candidate matches the candidate that actually produced a `GOOD` outcome. Comparison metrics are computed for the deterministic baseline scoring on the same held-out data, and the learned model is considered viable for further evaluation only if it outperforms the baseline by a statistically significant margin.

If the offline evaluation does not show a clear improvement over the baseline, the appropriate response is to defer activation, return to stage one, and accumulate more data. The threshold of one thousand rows is the minimum at which training is meaningful, not the threshold at which a useful model is guaranteed; some operational domains may require substantially more data before the learned signal exceeds the deterministic baseline.

### 8.2.4 Stage Three: Shadow Deployment

If the offline evaluation is positive, the next stage is shadow deployment. In this stage, the trained model is loaded into the FastAPI sidecar and served live, but the routing agent does not consult it for decisions. Instead, on every routing decision, the routing agent computes both its deterministic score and the learned model's score, logs both for analysis, and uses the deterministic score for the actual decision.

Shadow deployment provides two distinct kinds of validation that offline evaluation does not. The first is operational: the sidecar is exercised under realistic request rates, with realistic feature vectors produced by the live feature-builder rather than synthesized from historical logs. Any operational issue — a memory leak, a slow inference path, a request format mismatch — is surfaced in the shadow data rather than in production decisions. The second is empirical: the live decisions and their outcomes can be compared against the model's predictions, providing an additional layer of evidence that the model's offline performance generalizes to live operation.

Shadow deployment is performed for a duration sufficient to accumulate at least several hundred decisions with their outcomes; at typical operational rates, this is approximately four to six weeks. The data from this period is analyzed to identify any divergence between the model's predicted candidate ordering and the deterministic baseline's ordering, and to verify that the model's favored alternatives produce equal or better outcomes when the baseline's choice was substantially different.

### 8.2.5 Stage Four: Limited A/B Testing

If shadow deployment confirms the model's quality, the next stage is limited A/B testing. A small fraction of stores — perhaps ten percent, selected for their typical operational profile rather than for any particular characteristic — are switched to use the learned ranker for their actual routing decisions. The remaining ninety percent continue on the deterministic baseline. The drift-dashboard infrastructure described in Chapter 5 is extended to compute its metrics stratified by routing policy, so that the two cohorts can be compared on the operational metrics that matter (acceptance rate, good-verdict rate, first-time-fix rate, SLA compliance).

The duration of the A/B test is governed by statistical-significance requirements rather than calendar duration. A typical test requires accumulating enough decisions in the experimental cohort to detect a meaningful difference in good-verdict rate at conventional confidence levels; depending on the effect size, this may take six to twelve weeks of operation.

The decision criteria at the end of the A/B test are explicit. The learned ranker proceeds to full rollout if its good-verdict rate exceeds the baseline's by a statistically significant margin and its other operational metrics are at least equivalent. It is rolled back if its good-verdict rate is materially worse, or if any of its operational metrics show concerning regressions. The intermediate case — a small but not statistically significant improvement — typically results in extending the test rather than making a final decision, on the principle that the cost of extending is small and the cost of a premature commitment is large.

### 8.2.6 Stage Five: Full Rollout

If the A/B test confirms the model's superiority, the learned ranker is rolled out to all stores. This stage is operationally simple — it amounts to setting `ENABLE_LEARNED_RANKER=1` for all application instances and confirming that the sidecar is reachable from each instance — but it warrants explicit treatment because it is the moment at which the system's principal scoring mechanism transitions from a hand-tuned formula to a learned function.

The rollout should be monitored carefully for the first several weeks. The drift dashboards should be consulted daily during this period, with particular attention to metrics that might detect any subtle degradation: the explanation-failure rate (which would indicate sidecar issues), the rejection rate per provider (which might detect cases where the new model favors providers who reject more often), and the per-category good rate (which might detect category-specific regressions that did not appear in the A/B test). Any concerning pattern should trigger an immediate rollback to the deterministic baseline by clearing the `ENABLE_LEARNED_RANKER` flag.

The deterministic baseline remains in the codebase as the fallback path, exactly as it does in the current state. A rollback to it is therefore a single-flag change rather than a code revert, which is the appropriate level of operational reversibility for a change of this consequence.

### 8.2.7 Stage Six: Continuous Retraining Cycle

After full rollout, the system enters its steady operational state. The weekly retrain cron — which currently exists as a stub that exports data and reports readiness — is extended to actually trigger training when sufficient new data has accumulated since the previous training run. Each new model is evaluated against the current production model on a held-out validation set. The new model replaces the production model only if it demonstrates improvement; this is the blue-green deployment model described in Chapter 5.

The continuous retraining cycle is what converts the system from a one-time-trained learning system to a continuously-improving one. As operational reality shifts — new categories of equipment emerge, new providers join, geographic patterns evolve — the model is retrained on the most recent data and incorporates these shifts into its scoring. The deterministic baseline does not change; the learned model evolves around it.

This stage continues indefinitely. There is no terminal point at which the system is "done." The principal operational concern is to ensure that the retraining process itself remains well-calibrated — that the data quality remains high, that the moderator-verification rate does not degrade, that the exploration mechanism continues to produce sufficient counterfactual data — and to intervene when any of these inputs to the cycle shows signs of degradation.

### 8.2.8 Adjacent Future Work Beyond the Learned Ranker

The activation of the learned ranker is the principal future work, but several adjacent improvements would be appropriate to consider in conjunction with it.

The first is the activation of per-technician routing. The schema already supports per-technician assignment via the `TicketAssignment.assigned_user_id` foreign key, but the routing agent does not currently target individual technicians; it routes to providers and the providers select the technician. Activating per-technician routing would require extending the routing agent's candidate-set construction to include individual technicians (treating each as an effective "single-person provider"), extending the score formula to account for per-technician features (notably the skill embedding, which is already per-user), and extending the front-end and notification flows to address technicians directly. The schema work is done; the routing-agent and frontend work is approximately the scope of a small additional engagement.

The second is the introduction of more sophisticated exploration policies. The ε-greedy mechanism described in Chapter 4 is the simplest non-trivial bandit algorithm and is appropriate for the cold-start period. Once a learned ranker has been deployed and its uncertainty estimates are available, an algorithm such as Thompson Sampling or Upper Confidence Bound would produce more efficient exploration with lower operational cost. Such an algorithm would replace the current ε-greedy code in the routing agent's selection step; the surrounding exploration-logging infrastructure (the `was_exploration` flag, the decision log) would carry over unchanged.

The third is the introduction of multi-objective optimization. The current scoring formula treats the routing decision as a single-objective problem: maximize the score, where the score is a proxy for outcome quality. In production, the dispatch operator may have multiple objectives that are not perfectly aligned: outcome quality, fairness across providers (avoiding concentration of work with a small set of top performers), provider satisfaction (ensuring that exploration costs are spread fairly), and operational cost. A multi-objective ranking framework — perhaps a weighted combination of objectives or a Pareto-frontier approach — would express these competing objectives explicitly. This work is more substantial than the previous two and would benefit from being scoped to a dedicated engagement.

The fourth is the addition of incident-retrospective tooling. The system records every routing decision in detail and every outcome with structured fields, but the tooling for analyzing these records retrospectively — particularly when an unusual or operationally significant ticket has occurred — is currently minimal. A dedicated incident-review interface that surfaces the relevant decision log, outcome, rating, and explainer rationale alongside the ticket would substantially reduce the time required to learn from operational events.

### 8.2.9 The Long-Term Trajectory

The system's long-term trajectory, viewed from the perspective of the work performed during the internship, is one of continuous incremental improvement rather than periodic redesign. The architecture described in this report is structured to admit each of the future-work items above as a localized addition rather than a re-engineering of the system as a whole. The orchestrator can compose new agents; the schema can absorb new entities and columns; the frontend can grow new components; the drift dashboards can be extended with new metrics. None of these requires rewriting the system's core; each is an addition that the architecture is structurally prepared to accommodate.

This is the property the system was designed to have. The internship work was not a one-time delivery of a finished product; it was the construction of a foundation on which subsequent improvement can be made cheaply. The learned-ranker activation pathway described in this section is the most immediate and most consequential of these subsequent improvements, but it is not the last. As the system continues to operate, accumulate data, and evolve, the principles documented in this report — correctness by construction, operational defensibility, graceful degradation — should continue to guide the design of every addition. Each new component, like each component already in place, should be operationally correct from its first day of operation, observable in its failure modes, instrumented for retrospective analysis, and structured so that it can be replaced or refined without affecting the components around it.

The system that emerged from the internship is not the final version of the system, and was never intended to be. It is a deliberately incomplete artifact that has been designed with explicit awareness of what comes next. The principal contribution of the internship is therefore not the system as it currently runs, valuable though that is, but the architecture that determines how the system will grow.

## Closing Statement

This report has described the design and implementation of a smart ticket-routing and dispatch system, built during a six-month internship at Urban Guest, Magarpatta City, Pune. The system is a closed-loop, multi-agent dispatch engine with semantic feature augmentation, asynchronous reasoning, counterfactual decision logging, and a scaffolded learning pipeline. It has been verified end-to-end against a live production database, exercised under deliberate failure injection, and characterized for latency under typical load. It is structurally complete, operationally correct from its first ticket, and architecturally prepared for the gradual deployment of additional learned components as production data accumulates.

The work documented in this report was performed within the constraints of an internship engagement. It is not a complete production system in the sense that a multi-year engineering effort would produce, and the report has been explicit about the boundaries of what was and was not done. Within those constraints, however, the work performed is substantive: a routing system that did not previously exist has been built, the data foundation on which future improvements depend has been constructed, the documentation that will guide subsequent work has been written, and the engineering principles that should govern that work have been articulated.

The next stage of the system's lifecycle is the operational deployment of the work performed during the internship and the gradual activation of its learned components. The pathway from the current state to the fully operational future state has been described in this chapter and is supported by the design and infrastructure described in earlier chapters. The system is ready to take its next step.
